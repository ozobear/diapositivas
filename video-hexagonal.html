La tesis central

Misma aplicación, destinos opuestos

↗ Independencia tecnológica

La lógica de negocio no sabe qué es Express, Spring Boot, PostgreSQL o MongoDB. Es pura, testeable en milisegundos y evoluciona sola.

↘ Dependencia del Framework

Anotaciones de ORM por doquier, lógica de negocio metida en controladores HTTP y tests acoplados a la base de datos que tardan horas.

La herramienta no define la calidad de tu software. Tu arquitectura define su vida útil, y la tecnología solo la ejecuta.

Conceptos clave

El contrato y la implementación

1Dominio (Core)Entidades y reglas puras de negocio. Cero librerías externas.
2Puertos (Ports)Interfaces que definen QUÉ necesita o expone el sistema (In / Out).
3AdaptadoresImplementaciones concretas (Controllers, Repositorios SQL, SDKs).
4InyecciónEl pegamento que conecta los adaptadores a los puertos en runtime.
Comparativa de código

Del desastre acoplado al diseño desacoplado

❌ Mal: Acoplado al ORM
import { UserEntity } from './orm/user.entity';

export class CreateUser {
  async execute(data) {
    // Atado a TypeORM / Postgres
    return await UserEntity.save(data);
  }
}
✓ Bien: Usando un Puerto
import { UserRepository } from '../ports/user-repo';

export class CreateUser {
  constructor(private userRepo: UserRepository) {}

  async execute(cmd: RegisterCommand) {
    return this.userRepo.save(new User(cmd));
  }
}
Reglas de oro para testear

Tests rápidos, arquitectura saludable

Checklist de Verificación de Dominio

  • ✓Casos de uso probados en memoria con Mocks sencillos.
  • ✓Cero frameworks involucrados en tests unitarios.
  • ✓Cientos de pruebas ejecutadas en milisegundos.

Matriz de Criticidad en Adaptadores

Adaptadores Secundarios (BD / APIs): Pruebas de integración aisladas con Testcontainers.

Adaptadores Primarios (HTTP / CLI): Pruebas End-to-End o contratos API.

Checklist de validación

¿Es realmente hexagonal tu código?

  • ✓¿Puedo probar mis casos de uso sin levantar la base de datos ni la API HTTP?
  • ✓¿Las reglas de negocio están totalmente libres de anotaciones o decoradores del ORM?
  • ✓¿El dominio utiliza el lenguaje del negocio (Ubiquitous Language) y no términos de bases de datos?
  • ✓¿Todas las dependencias del proyecto apuntan estrictamente hacia el centro (Dominio)?
Conclusión

No dejes que el Framework dicte tu lógica.
Haz que el Dominio gobierne tu aplicación.

Proteger las reglas del negocio es proteger el valor real de tu proyecto.
